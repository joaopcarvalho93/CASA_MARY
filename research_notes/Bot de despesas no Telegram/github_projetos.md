# Open-source Telegram (and WhatsApp) expense / receipt bots on GitHub: reference catalogue for a Supabase + Deno household bot

Method note (applies to all sections): repo metadata (stars, forks, created date, GitHub `updated_at`) comes from GitHub repository search run on 2026-09-30. "Last commit" is the date of the HEAD commit on the default branch, obtained by shallow-cloning each repo on 2026-09-30 (it is more reliable than GitHub's `updated_at`, which also changes when someone stars a repo). Feature descriptions come from each repo's README and, where stated, from reading the source files. Almost every project in this niche is small (0 to 80 stars). Stars do not tell you much about quality here, so code-level signals (tests, idempotency, schema) matter more. grammy.dev, supabase.com and core.telegram.org could not be fetched directly (egress blocked). grammY docs were read from their GitHub source (grammyjs/website), Supabase's example from the supabase/supabase repo, and the Telegram and Supabase limits via search-result snippets.

## Q1. Which GitHub projects are Telegram expense / receipt / household-budget bots, and how do they work?

### Takeaway
There is no large, dominant open-source project. The most-starred Telegram expense bots have fewer than 80 stars, and the best-known one (muety/telegram-expense-bot, 70★) is archived. The most useful references are recent small projects with good engineering: Tallyo (rules-first parser, LLM fallback, DB-backed confirm state machine, idempotent commit, 124 tests), yelinaung/expense-bot (Go + Postgres + Gemini receipt OCR, inline edit, draft expiry, CI), actual-budget-telegram-bot (no-LLM keyword parser that learns categories, household group, Google Vision OCR), hreluz/telegram-expense-worker (CF Worker + Neon Postgres, inline category picker, undo button) and izomba-lang/receipts-bot (Claude Vision + Supabase + Storage, dedup by file hash).

**Best-engineered recent Telegram expense bots**
- **Germageddon/tallyo**: https://github.com/Germageddon/tallyo. 3★, TypeScript, created 2026-07-25, last commit 2026-08-01. A public instance runs as @TallyoBot. Input is plain language (`coffee 5, gas 10`, several items per message). A **rules parser handles simple entries and an AI fallback (Groq/OpenAI/Ollama) handles messy phrasing; the AI output "is validated so it can never invent an amount"**. Money is stored as **integer cents**, with historical ECB FX rates. Storage is SQLite with versioned migrations. The architecture is ports-and-adapters (CLI and Telegram adapters, with WhatsApp/Discord as "one more adapter"). It has **124 offline tests** and a CI gate — [README](https://github.com/Germageddon/tallyo)
  - From DESIGN.md: parses are **confidence-gated**. Unambiguous ones auto-save with a one-tap **Undo**. Ambiguous or low-confidence ones show a confirm card. The confirm/edit loop state lives in a DB table `pending_captures` (FSM `IDLE → AWAITING_CONFIRM(id) → AWAITING_EDIT(id)`), because grammY's in-memory session would not survive a redeploy. **Idempotent commit**: `UPDATE pending_captures SET status='committed' WHERE id=? AND status='pending'`, with expenses inserted in the same transaction only if that UPDATE changed a row. **Amount grounding**: every amount the LLM returns must have its digits present in the source text, otherwise the parse is LOW_CONFIDENCE. Other features: soft-delete with `deleted_at`, `/undo`, `/delete 412` by id, a `setMyCommands` menu, per-user rate limits and LLM quotas, and a user id required on every repository method — [DESIGN.md](https://github.com/Germageddon/tallyo/blob/main/docs/DESIGN.md)

### Inferences
- The Telegram expense-bot space is fragmented, and hobby projects make up most of it. No project is a mature "product" to fork. Copying patterns (parser, confirm FSM, idempotency, receipt pipeline) from several small repos is more realistic than adopting one codebase.
- Receipt processing has shifted from classic OCR (Google Cloud Vision, used by actual-budget-bot and el-rapido) to **single-call vision LLMs** (Gemini 2.5 Flash, Claude Vision, GPT-4 Vision), which return structured fields directly. QR-code parsing of fiscal receipts is rare (finalytic is the only example found). It would be a good fit for Portugal's ATCUD/fiscal QR codes, but no open-source Telegram bot implementing the Portuguese QR standard was found.
- Several of the best-engineered repos disclose that AI coding agents wrote them (yelinaung) or read like it. Read the code before copying it.

### Gaps
- Nhqvu2005/Expense-Tracker-Bot (49★): README fetch failed, so input format, storage and features are unverified.
- Last-commit dates were not collected for keithlowc, kaiimran, finalytic and several Sheets-based bots.
- No open-source Telegram bot parsing **Portuguese fiscal QR codes (ATCUD/e-fatura)** was found. Other researchers may cover this.

## Q2. Which projects run on Supabase Edge Functions / Deno / Cloudflare Workers / serverless webhooks (most relevant)?

### Takeaway
There is an official Supabase + grammY Edge Function example, and at least six public repos run a Telegram expense bot as a **Supabase Edge Function (Deno)**. They are 0-star personal apps and some look Lovable/AI-generated, but several show production-grade patterns: header `secret_token` check, `update_id` idempotency via a Postgres RPC or unique constraint, and comma-decimal parsing. The richest is **kompaniy12-creator/finbot** (grammY webhook on Edge Functions, Claude Vision receipts, pg_cron, retry queue, inline confirmation for large amounts). The cleanest small reference is **17sTomy/finance-app** (a roughly 60-line index.ts with a dependency-injected handler, a DB receipt for dedup and an es-AR amount parser). On Cloudflare Workers there are several good examples: tdzr-bot (grammY + D1, household/roommate splitting), hreluz/telegram-expense-worker (Neon Postgres), Sigmakib2/smart-ledger-bot (Hono + D1), nomad-expense (grammY + Postgres, family sharing) and the MoshrefBashi/SplitTabs split bots.

### Cited Findings

**Official scaffolding**
- The Supabase repo ships `examples/edge-functions/supabase/functions/telegram-bot/index.ts`. It uses `import { Bot, webhookCallback } from 'npm:grammy@^1'`, `webhookCallback(bot, 'std/http')`, and checks `url.searchParams.get('secret') !== Deno.env.get('FUNCTION_SECRET')`, returning 405 on mismatch. It is deployed with `supabase functions deploy --no-verify-jwt telegram-bot`, and the webhook is set to `https://<PROJECT_REFERENCE>.supabase.co/functions/v1/telegram-bot?secret=<FUNCTION_SECRET>` — [supabase/supabase example index.ts](https://github.com/supabase/supabase/blob/master/examples/edge-functions/supabase/functions/telegram-bot/index.ts); [example README](https://github.com/supabase/supabase/tree/master/examples/edge-functions/supabase/functions/telegram-bot)
- grammY's hosting guide for Supabase: you "need to run your bot on webhooks… use `webhookCallback` and not call `bot.start()`". JWT verification must be disabled "because Telegram uses a different way to make sure the requests are coming from Telegram". "There is no file system on Supabase Edge Functions". The example code lives in grammyjs/examples `setups/supabase-edge-functions` — [grammY docs source: hosting/supabase.md](https://github.com/grammyjs/website/blob/main/site/docs/hosting/supabase.md)
- grammY's deployment-types guide says `webhookCallback` has a **default 10-second timeout**. If middleware does not finish in time, Telegram re-sends the update, "your bot will not just see the update two times, but a few dozen times". Using the `"return"` timeout mode can cause race conditions and data loss. Long work should go to a queue — [grammY docs source: deployment-types.md](https://github.com/grammyjs/website/blob/main/site/docs/guide/deployment-types.md)
- Supabase Edge Functions: requests must be answered within 150 s on both Free and Pro. `EdgeRuntime.waitUntil(promise)` keeps the worker alive for background tasks up to 150 s (Free) or 400 s (paid), but "does not extend the hard wall clock limit" — [Supabase Background Tasks docs (via search)](https://supabase.com/docs/guides/functions/background-tasks); [Supabase limits (via search)](https://supabase.com/docs/guides/functions/limits); [Supabase blog](https://supabase.com/blog/edge-functions-background-tasks-websockets)

### Inferences
- For a Supabase + Deno + Lovable Cloud app, the most directly copyable layout is **17sTomy/finance-app**: a thin `index.ts` with `Deno.serve`, a pure testable `handler.ts` with an injected gateway, and a pure `parser.ts`, with persistence done through Postgres RPCs (`record_telegram_expense` keyed by `(bot_id, update_id)` / `(chat_id, message_id)`). Add FinTrackApp's `claim_telegram_webhook_update` gate and finbot's `pending_retry` + pg_cron retry for slow AI or receipt steps.
- Use the `X-Telegram-Bot-Api-Secret-Token` header (via `setWebhook secret_token`) rather than the `?secret=` query string in Supabase's example, because the header keeps the secret out of URLs and logs. The more careful repos (17sTomy, FinTrackApp, gastito, finflow) all use the header.
- Vision-LLM receipt processing can exceed grammY's 10 s `webhookCallback` timeout. Two patterns fit: (a) ack fast and process in `EdgeRuntime.waitUntil` (capped at 150/400 s), or (b) write a job row and let pg_cron/pg_net call a worker function, as finbot does. Both need update-level dedup.
- The Cloudflare Worker bots (tdzr-bot, hreluz) face the same stateless constraint as Supabase Edge Functions. They keep conversation state in DB tables (`pending_inputs`, `pending_captures`, `pending_actions`) instead of in-memory sessions, and that pattern transfers directly to Supabase.

### Gaps
- No Supabase-Edge Telegram expense bot with meaningful community adoption (stars, forks, issues) exists. All found are personal 0★ apps, so their code quality varies and some are likely AI-generated (possibly Lovable).
- The SQL bodies of `claim_telegram_webhook_update` (FinTrackApp) and `record_telegram_expense` (17sTomy) were not read. Their exact uniqueness constraints are inferred from the parameter names.
- The Supabase limits page and the Telegram Bot API page could not be fetched directly (egress blocked). Those figures come from search snippets of the official pages.
- The grammyjs/examples `setups/supabase-edge-functions` repo was not opened.

## Q3. Which projects handle shared household expenses between two people (who paid, 50/50 split, balance owed)?

### Takeaway
Two-person household bots mostly record **who paid** and show per-person breakdowns; few compute a running "who owes whom" balance. Proper split and settle logic is found in group bill-splitting bots (tdzr-bot, MoshrefBashi/Dong, SplitTabsBot, SettleExpensesBot, splitgram), which use integer cents, equal or custom shares, and greedy minimum-transfer settlement. For a couple, the simplest reference combination is nowjordanhappy/expense-tracker-bot's `paid_by` + `/summary` by person, tdzr-bot's inline payer/split buttons, and a settle view.

### Cited Findings
- **nowjordanhappy/expense-tracker-bot**: https://github.com/nowjordanhappy/expense-tracker-bot. 0★, Python (python-telegram-bot 21.6) + **Supabase**, hosted on an Oracle Cloud free VM. Created and last committed 2026-04-14. "Tracking **shared household expenses**… split by person". Commands: `/add <amount> <description> @username` (paid by someone else), a step-by-step `/add` flow with **inline category buttons**, `/mine`, `/summary` (breakdown by person), `/categories`. - **lucasmenendez/SettleExpensesBot**: https://github.com/lucasmenendez/SettleExpensesBot. 4★, Go. Last commit 2024-01-25, likely inactive. "Manage group expenses and calculate the best options to pay" — [GitHub search metadata](https://github.com/lucasmenendez/SettleExpensesBot)

### Inferences
- For a two-person household, the useful data model is `expenses(paid_by_member_id, amount_cents, split_mode {equal|custom|payer_only}, share_a_cents, share_b_cents)` plus `settlements(from, to, amount_cents)`. Balance owed is Σ(paid − share) per person, and with 2 people the "minimum transfers" algorithm reduces to a single number. tdzr-bot's rules (integer cents, default payer = sender, default equal split, inline buttons to change, then settle) are the closest template.
- "Who paid" is best inferred from the Telegram `from.id` mapped to a household member (tdzr-bot, nowjordanhappy, actual-budget-bot), with an override (`@username` or an inline payer button).

### Gaps
- No repo was found that combines Supabase Edge Functions with a two-person 50/50 running balance in a Telegram bot. gastito has a percentage-share view but it is web-based, not bot-based.

## Q5. What patterns recur (amount grammar incl. comma decimals, category inference, confirm-before-save, undo, idempotency on webhook retries)?

### Takeaway
The recurring best practices are:
- a deterministic parser first (amount + optional currency + description, comma-decimal aware), with an LLM only as a fallback and never trusted to invent amounts;
- money stored as integer cents;
- categories from a keyword dictionary that learns from user corrections, or an LLM/embedding with confidence;
- auto-save plus a one-tap inline "Undo" for confident parses, and an inline confirm card for OCR/LLM or large amounts;
- conversation state in DB tables, not memory, on serverless;
- update-level idempotency (`update_id` / `message_id` unique claim) with a fast 2xx, and a retry queue for slow work.

### Cited Findings

**Amount grammar / comma decimals**
- 17sTomy parser: accepts `3000`, `3.000,50` and `USD 20`. A regex distinguishes thousands-dot plus comma-decimal (`^\d{1,3}(?:\.\d{3})+(?:,\d{1,2})?$`) from a simple `\d+([.,]\d{1,2})?`. It rejects values ≤ 0, and the help text tells the user "Use a comma for cents: 3.000,50" — [parser.ts](https://github.com/17sTomy/finance-app/blob/main/supabase/functions/telegram-expense/parser.ts); [handler.ts](https://github.com/17sTomy/finance-app/blob/main/supabase/functions/telegram-expense/handler.ts)
- FinTrackApp: a naive `parseFloat(args[0].replace(',', '.'))` — [index.ts](https://github.com/zorgoalex/FinTrackApp/blob/main/supabase/functions/telegram-bot/index.ts)
- yelinaung: both orders (`5.50 Coffee`, `Coffee 5.50`) and a currency symbol prefix (`$10 Lunch`) — [README](https://github.com/yelinaung/expense-bot)
- hreluz: fixed grammar `<amount> <category> [@YYYY-MM-DD] [note]` with an optional date token anywhere after the category — [README](https://github.com/hreluz/telegram-expense-worker)
- MoshrefBashi: arithmetic expressions in amounts (`45000+12000`, `150000/3`) — [README](https://github.com/mohasara/Dong-Telegram-Bot)
- Localized shorthand: `50rb`, `1jt`, `500k` (irfan-yulianto) — [README](https://github.com/irfan-yulianto/Telegram-Finance-Bot)
- Multi-item messages: `coffee 5, gas 10` (Tallyo), and «кофе 12 zł и булочка 5 zł» → 2 rows (finbot) — [Tallyo README](https://github.com/Germageddon/tallyo); [finbot README](https://github.com/kompaniy12-creator/finbot)
- Integer minor units: Tallyo (ISO-4217 exponent map, HALF_EVEN) and tdzr-bot (cents; remainder distributed by member order) — [Tallyo DESIGN.md](https://github.com/Germageddon/tallyo/blob/main/docs/DESIGN.md); [tdzr-bot README](https://github.com/nin39six/tdzr-bot)
- Timezone-correct dates: 17sTomy derives the date from Telegram `message.date` in a fixed IANA zone. gastito uses America/Santiago. muety asks for the user's location — [parser.ts](https://github.com/17sTomy/finance-app/blob/main/supabase/functions/telegram-expense/parser.ts); [gastito README](https://github.com/wladimick/gastito-control-gastos); [muety README](https://github.com/muety/telegram-expense-bot)

**Category inference**
- Keyword dictionary that learns: actual-budget-bot "asks once for unknown words, remembers forever" — [README](https://github.com/bbharathbala/actual-budget-telegram-bot)
- Inline picker for unknown categories: hreluz shows existing categories plus "Keep 'typed'" — [README](https://github.com/hreluz/telegram-expense-worker)
- Deterministic match against the user's own categories (accent-insensitive, whole-word, longest match, null on tie): 17sTomy — [parser.ts](https://github.com/17sTomy/finance-app/blob/main/supabase/functions/telegram-expense/parser.ts)
- Embedding kNN (Supabase.ai gte-small) with an LLM fallback, requiring confirmation when confidence is not "high": finbot — [README](https://github.com/kompaniy12-creator/finbot); [bank_pipeline.ts](https://github.com/kompaniy12-creator/finbot/blob/main/supabase/functions/tg-webhook/bank_pipeline.ts)
- LLM with a fixed category list (SARRAF: 16 categories; Tallyo: 10; porquinapp: few-shot Portuguese examples mapping to categoria + tipo_pagamento) — [SARRAF README](https://github.com/emaan-gul/SARRAF-BOT); [Tallyo DESIGN.md](https://github.com/Germageddon/tallyo/blob/main/docs/DESIGN.md); [porquinapp webhook](https://github.com/TheRibeiro/porquinapp/blob/main/supabase/functions/telegram-webhook/index.ts)
- An inbox of unparsed messages for manual correction: gastito — [README](https://github.com/wladimick/gastito-control-gastos)

**Confirm-before-save vs auto-save + undo**
- Confidence-gated: auto-save plus a one-tap Undo when unambiguous, a confirm card otherwise (Tallyo). Inline Yes/Edit/Cancel only above 200 PLN, with auto-confirm after 60 s (finbot). Confirmation for money-changing AI-inferred actions (smart-ledger-bot). A confirm step after OCR extraction (el-rapido). Unconfirmed drafts expire (yelinaung) — [Tallyo DESIGN.md](https://github.com/Germageddon/tallyo/blob/main/docs/DESIGN.md); [finbot README](https://github.com/kompaniy12-creator/finbot); [smart-ledger README](https://github.com/Sigmakib2/smart-ledger-bot); [el-rapido README](https://github.com/el-rapido/expensetracker); [yelinaung README](https://github.com/yelinaung/expense-bot)
- Undo: `/undo` is nearly universal (actual-budget-bot, hreluz with an inline 🗑 button, Tallyo, SARRAF `undo_last`, izomba soft-delete + `/undo` restore, finbot, smart-ledger-bot) — sources as above plus [izomba README](https://github.com/izomba-lang/receipts-bot)
- Edit: `/edit <id> field=value` (izomba), inline edit/delete buttons (yelinaung), natural-language correction (vijith, WhatsApp), and re-pipelining on Telegram `edited_message` (finbot) — [izomba](https://github.com/izomba-lang/receipts-bot); [yelinaung](https://github.com/yelinaung/expense-bot); [vijith](https://github.com/vijithsreevalsam/WhatsappBotForExpenseTracker); [finbot](https://github.com/kompaniy12-creator/finbot)
- Stateless multi-step flows persist in DB tables: `pending_inputs` (tdzr-bot), `pending_captures` (Tallyo), `pending_actions` (smart-ledger), `telegram_log.status='pending_card_type'` (porquinapp) — [tdzr-bot](https://github.com/nin39six/tdzr-bot); [Tallyo DESIGN.md](https://github.com/Germageddon/tallyo/blob/main/docs/DESIGN.md); [smart-ledger](https://github.com/Sigmakib2/smart-ledger-bot); [porquinapp](https://github.com/TheRibeiro/porquinapp/blob/main/supabase/functions/telegram-webhook/index.ts)

**Idempotency on webhook retries**
- Telegram retries non-2XX responses and grammY warns about duplicate processing after timeouts (10 s default) — [grammY deployment-types.md](https://github.com/grammyjs/website/blob/main/site/docs/guide/deployment-types.md); [Telegram Bot API (via search)](https://core.telegram.org/bots/api)
- Implementations seen:
  - `claim_telegram_webhook_update(p_update_id)`: if not claimed, return 200 (FinTrackApp) — [index.ts](https://github.com/zorgoalex/FinTrackApp/blob/main/supabase/functions/telegram-bot/index.ts)
  - an RPC keyed by `(bot_id, update_id, chat_id, message_id)` plus a `telegram_receipts.replied_at` column, returning 503 on transient failure because "The DB receipt prevents duplicate expenses" (17sTomy) — [handler.ts](https://github.com/17sTomy/finance-app/blob/main/supabase/functions/telegram-expense/handler.ts)
  - `message_log ON CONFLICT DO NOTHING` plus `unique nulls not distinct` on expenses, and a `pending_retry` table retried by pg_cron (finbot) — [SPEC.md](https://github.com/kompaniy12-creator/finbot/blob/main/SPEC.md)
  - receipt-file hash dedup (izomba) — [README](https://github.com/izomba-lang/receipts-bot)
  - an idempotent state-machine commit (Tallyo) — [DESIGN.md](https://github.com/Germageddon/tallyo/blob/main/docs/DESIGN.md)
  - a jobs table with `message_sid` (bchhabra, WhatsApp) — [README](https://github.com/bchhabra2490/whatsapp-bot)
  - an admin `/droppending` escape hatch (hreluz) — [README](https://github.com/hreluz/telegram-expense-worker)
- Access control: allowlists of Telegram user IDs (yelinaung, nowjordanhappy, Tallyo private-by-default, smart-ledger `ALLOWED_USER_ID`), account linking via a `/start <token>` deep link (17sTomy, porquinapp, gastito, FinTrackApp), and private-chat-only enforcement (17sTomy, FinTrackApp) — sources as cited above.

### Inferences
- Recommended grammar for a Portuguese household bot, synthesized from the above: `[descrição] <valor> [descrição]` with the amount matched by `(\d{1,3}(?:\.\d{3})+|\d+)(?:,\d{1,2})?` or dot-decimal, an optional `€`/`eur`, optional `@data` or `ontem`, and optional `#tag`. Parse to integer cents, and only fall back to an LLM (validated with amount grounding) when the regex fails. This mirrors 17sTomy's parser and Tallyo's design.
- A good default UX: auto-save a confident text parse and reply with a message carrying inline `[↩️ Desfazer] [✏️ Categoria] [👤 Quem pagou]` buttons. Always show a confirm card for receipt photos processed by a vision LLM. This combines hreluz, Tallyo, tdzr-bot and finbot.
- Idempotency should be enforced in Postgres (a unique `telegram_update_id` or `(chat_id, message_id)` claim row inserted first, inside the same transaction or RPC as the expense insert), because Edge Function instances are stateless and Telegram delivers at least once.

### Gaps
- No project was found that specifically handles European Portuguese phrasing (e.g. "café 3,50", "paguei 20€ no Continente"). porquinapp handles Brazilian Portuguese via Gemini few-shot prompting only.
- The quantitative accuracy of LLM versus rules parsing was not measured in any repo examined.
